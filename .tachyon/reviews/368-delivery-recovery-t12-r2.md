Both `salvageQuarantine`/`abandonQuarantine` are now thin wrappers (`leaseService.ts:395-398`, `436-442`) around `*Internal` implementations, routing every failure through a new `recoveryFailure` helper (`leaseService.ts:945-966`) that: first re-attempts `replayRecovery` (covering same-operation lost-response/concurrent-duplicate replay without rerunning fence/inspection/approval/id-allocation); wraps any `DeliveryStoreBusyError` (from the replay attempt, the original failure, or the winner re-read) via `this.busy()`; passes through any `DeliveryLeaseError` that isn't the internal `recoverySnapshotChanged`-tagged marker unchanged (definitive refusals like authority denial, malformed inventory, fence/approval failure, `DELIVERY_WORKTREE_MISMATCH` are not muddied); and otherwise re-reads the actual winner and classifies it precisely as the contract specifies — abandoned → `DELIVERY_ABANDONED`, in-flight-owned → retryable `WORKTREE_OCCUPIED`, quarantined → its durable `reconcileRefusal` with the real persisted reason, anything else → non-retryable `DELIVERY_INVALID_STATE`. `proveRecoveryEmpty`, `recoveryInventory`, and `recoveryApproval` (`leaseService.ts:895-903`, `919-923`, `925-935`) now each catch their dependency's throw and convert it to a structured, non-retryable `DELIVERY_QUARANTINED` refusal rather than leaking an arbitrary exception, satisfying "Approval, fence, and inspection throws/malformed results become structured non-retryable quarantine refusals."

**Residual gap.** `assertRecoverySnapshot` (`leaseService.ts:913-917`) is invoked from two call sites: inside `recoveryCurrent` (using the *original*, early snapshot taken by `recoverySnapshot` before the fence proof) and inside each `store.update` mutate callback (using the same snapshot). Tracing `DeliveryStore.update` (`store.ts:241-260`): its own outer `observed.version !== expectedVersion` check runs *before* `mutate()` is ever invoked, and every successful mutation unconditionally increments `version` — so any drift injected via a direct `store.update` call (as every new concurrency/tail-drift test in this correction does) is caught by that outer version check and reported through `recoveryFailure`'s winner-classification, not through `assertRecoverySnapshot`'s new tail comparison. Concretely: `it.each(["close","append"])("refuses a store-legal tail-only %s while the quarantine lease is unchanged", ...)` and `"classifies a pre-CAS different-operation winner..."` both inject their mutation from inside the `inventory()` callback, which runs *after* `recoveryCurrent` has already completed — so they exercise the version-conflict path, not the `assertRecoverySnapshot`-via-`recoveryCurrent` path the M1 fix specifically targeted (the fence-proof window between `recoverySnapshot()` and `recoveryCurrent()`). The fix itself is correct and is unconditionally invoked on every commit attempt, so no live gap results — the outer store CAS is a genuine, always-present backstop for this specific call site — but no test in this correction isolates and forces a tail-only drift landing specifically inside that narrower fence-proof window, so the tail half of `assertRecoverySnapshot`'s comparison remains verified only by code inspection, not by a dedicated regression. Low severity; does not block acceptance.

Minor, non-blocking cosmetic note: `recoveryFailure`'s quarantined-winner branch reuses `reconcileRefusal`, whose fixed message ("dead holder could not be safely reconciled") was written for T11's reconciliation flow and reads slightly oddly for a recovery-race context; the code (`DELIVERY_QUARANTINED`) and `detail.evidence` (the real persisted reason) are correct regardless.
