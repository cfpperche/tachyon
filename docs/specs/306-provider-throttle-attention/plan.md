# 306 — provider-throttle-attention — plan

_Drafted from `spec.md` on 2026-06-30. The approach, not the steps (those go in `tasks.md`)._

## Approach

Extend `AttentionState` (`src/attention/AttentionMonitor.ts:4`) from `"working" | "idle" | "needs-input"` to add `"throttled"`. Add a new, separate pattern list `PROVIDER_ERROR_PATTERNS` in `src/attention/patterns.ts` and a `classifyError(paneText)` function (same tail-window-scan shape as `classifyTail`, but its own list — kept out of `DEFAULT_PATTERNS` per the spec's acceptance criterion, so tuning one never risks the other's precision).

In `AttentionMonitor.tick()` (`:138-166`), when pane content is stable (`content === snap.content`, same branch that currently checks `classifyTail` then falls through to idle), classify the tail with a **single unified bottom-up walk** — **(revised per design dueto finding 1, replacing the original "check classifyError globally before classifyTail" approach)**: `classifyError` and `classifyTail` each independently scan the whole tail window bottom-up and return their own best match, so calling them as two separate full-window passes with error checked first would let a STALE error line (still inside the `TAIL_WINDOW`, but above a newer line) beat a fresher, more-bottom prompt match — e.g. "Rate limit hit..." scrolled up, followed later by a genuine "Switch provider? [y/n]" prompt. The fix: walk the tail lines bottom-up ONCE; at each line, check the error patterns and the prompt patterns; the first line (closest to the bottom) that matches **either** wins; if that specific line matches both, error wins the tie-break (a line that's simultaneously an error banner and prompt-shaped is still fundamentally a provider error). This keeps the two pattern lists separate and independently tunable (satisfying the spec's "kept apart" acceptance criterion) while making recency — not category — the primary ordering signal. On a stable match (same `PATTERN_STABLE_MS` gate the prompt path already uses — no new debounce constant needed), transition to `throttled` or `needs-input` per which list matched.

The "notify only after it's been sustained" anti-spam rule needs one addition beyond the existing "notify on transition" model: `transition()` today only fires `onChange` when the state *changes*. Add a **second call site** in `tick()`, after the normal per-agent processing, that when `snap.state === "throttled"` and unchanged, checks `now - snap.stateSince >= THROTTLE_NOTIFY_DELAY_MS` and `snap.notifiedEpisode !== snap.stateSince`; if so, stamp `notifiedEpisode` and fire `onChange` again with the same state and `notify: true` (a "sustained-state" notify, distinct from `transition()`'s "state-changed" notify — same underlying `notifiedEpisode` field, same one-shot-per-episode contract `needs-input` already uses). `Workspace.ts`'s `onChange` wiring (`:423-442`) gets one more `else if` branch alongside the existing `needs-input` toast branch, reusing `this.host.notify` and the same "suppress if `terminals.isActive(agent)`" rule.

On the view-model side: add `"throttled"` to `AgentStatus` (`src/sidebar/types.ts:7`) so the sidebar dot is visually distinct from `needs`/`idle`/`running` (not just a badge on top of an unrelated dot color) — a throttled agent isn't "idle" (it's blocked, not free) and isn't "needs input" (nothing the user types will unblock a rate limit). `statusOf()` (`src/sidebar/agentModel.ts:36-42`) gains `if (attention === "throttled") return "throttled";` ahead of the `needs-input`/`idle` checks. `toAgentVM()`'s attention-label mapping (`agentModel.ts:45`) gains a `"throttled"` passthrough so the existing generic `{a.attention && <span class="badge attn">{a.attention}</span>}` in `AgentBadges` (`App.tsx:72`) renders it with zero new App.tsx badge code.

## Key decisions

- **A brand-new `AttentionState`/`AgentStatus` value `"throttled"`, not a badge bolted onto the existing `idle` status** — chosen because a provider error is semantically distinct from both "waiting for you" (`needs`) and "nothing to do" (`idle`); collapsing it into either would make the dot color lie about what's actually happening. Rejected: badge-only (keep status `idle`, add `attention: "throttled"` badge) — cheaper, but a maintainer scanning dot colors across a fleet of agents would still read a throttled agent as merely idle, which is exactly the blind spot the pin complains about.
- **A single unified bottom-up tail walk (bottom-most match wins; same-line ties go to error), not "always check error globally first"** — chosen (revised from the original plan per design dueto finding 1) because two independent full-window scans let a stale error line beat a fresher prompt line further down the pane. Rejected (the original plan's approach): calling `classifyError` unconditionally before `classifyTail` — would misfile a real, newer "needs your input" prompt as still-throttled whenever an older error banner happened to sit anywhere in the 8-line tail window, which is the opposite failure mode from the one this spec set out to fix.
- **A separate `PROVIDER_ERROR_PATTERNS` list + `classifyError()`, not folded into `DEFAULT_PATTERNS`/`classifyTail`** — chosen so the two concerns (interactive prompts vs. provider errors) can be tuned independently; spec 188 was deliberate about `DEFAULT_PATTERNS` precision ("broad patterns... deliberately excluded"), and error signatures are a different false-positive risk profile that shouldn't share a list with high-precision `[y/n]`-style prompts. **(Folded, dueto finding 2):** bare `/\b429\b/`/`/\b529\b/` are too risky standalone (429/529 could appear as a port number or in unrelated chat) and plain "API Error" without more context is too generic (would misclassify ordinary CLI failures that should stay inspectable, not "throttled"). `PROVIDER_ERROR_PATTERNS` ships with codex's proposed contextual list instead:
  ```
  /\b(rate[- ]?limit(?:ed|ing)?|too many requests|quota exceeded|usage limit|request limit)\b/i
  /\b(overloaded|server overloaded|temporarily unavailable|capacity exceeded|at capacity)\b/i
  /\b(?:api|provider|http|status|error|request)[^\n]{0,60}\b(?:429|529)\b/i
  /\b(?:429|529)\b[^\n]{0,60}\b(?:api|provider|http|status|error|rate|overload|capacity)\b/i
  /\b(?:try again later|please try again)\b[^\n]{0,80}\b(?:rate|overload|capacity|429|529)\b/i
  ```
- **A "sustained-state" second onChange call in `tick()`, not a `setTimeout`/timer** — chosen because `AttentionMonitor` is explicitly "pure state-machine" (`MonitorIO` injected, no wall-clock timers) per its own doc comment; the existing tick-driven model already re-evaluates every agent on each poll, so checking "has it been throttled long enough" on each tick is consistent with how `idle`'s `silenceSec` threshold already works, and keeps the class fully synchronous/unit-testable (`io.now()` injected, no real timers in tests). Rejected: a `setTimeout` per throttled agent — breaks the "no I/O side effects beyond the injected `MonitorIO`" contract and complicates cleanup when an agent stops mid-timer. **(Dueto finding 4 — no objection to the design, implementation guidance folded):** the sustained-notify check must live INSIDE the same per-agent loop, right after classification (where `snap` is already the live, tracked snapshot) — NOT as a separate pass iterating stored snapshots — so an agent that stopped/was dropped this tick (removed from `this.snaps` earlier in `tick()`) can never fire a stale notify.
- **The anti-spam delay is a hardcoded exported constant (`THROTTLE_NOTIFY_DELAY_MS`), not a new `tachyon.yml` setting** — chosen to match the spec's explicit non-goal (no new config surface for v1) and `PATTERN_STABLE_MS`'s own precedent (also a hardcoded constant, not configurable). Rejected: a per-agent `attention.throttledNotifyDelaySec` schema addition — real scope growth (schema, docs, `loadConfig.ts` validation) for a v1 whose main job is proving the detection signal is worth having at all.
- **Sidebar dot reuses `var(--ds-warn)` (no new CSS custom property), distinguished from `needs` by dropping the glow AND adding a visible border, not glow-removal alone** — chosen to avoid inventing a new design-system color for a fifth status when the existing palette (`--ds-ok`/`--ds-warn`/`--ds-err`/`--idle`) already covers "fine / pay attention / broken / nothing running." Rejected: reusing `--ds-err` (red) — too easily confused at a glance with `crashed`. **(Folded, dueto finding 5):** glow-removal alone was judged too subtle — in a compact context (status chips, a quick glance across many rows) an amber dot minus a glow can still read as plain `needs`. `.sdot.throttled` adds a visible `1px solid` darker-amber outline (`color-mix(in srgb, var(--ds-warn) 65%, black)`) on top of the `--ds-warn` fill, on top of the glow removal, and `STATUS_LABEL.throttled = "Throttled"` is added so it also appears correctly in the header's `StatusChips` counts (`App.tsx` `STATUS_ORDER`), not just the row badge.
- **`src/sidebar/actions.ts`'s `isRunning` predicate includes `"throttled"`** — **(new decision, folded from dueto finding 3, not in the original plan):** `isRunning` (`actions.ts:35`) gates `reanchor`/`reinjectContinuity` to `"running" | "needs" | "idle"`; without adding `"throttled"` there, a throttled agent — still a live process, still an AI agent — would silently lose those running-only actions the moment it entered the new status. Rejected: leaving it as-is and treating the gap as acceptable — a throttled agent is exactly the case where a maintainer might want to reanchor/reinject continuity while waiting out the provider, so silently disabling that is a regression, not a neutral omission.

## Risks & unknowns

- **R1 — false positives.** Resolved by the design dueto (finding 2): no bare `/\b429\b/`/`/\b529\b/` or unqualified "API Error" — every pattern requires a co-occurring rate/capacity/error-context word within a bounded window (see the folded regex list above). Residual risk is a code review or chat transcript that happens to combine those words within 60-80 chars of a 429/529 — judged acceptable for v1 given the specificity.
- **R2 — false negatives across runtimes.** Claude and Codex CLIs likely phrase provider errors differently (and future runtimes differently still). Mitigation: v1 explicitly scopes to patterns observed in current local usage (mirrors spec 305's own non-goal wording for Codex normalization) — a documented, contained gap, not a blocking unknown.
- **R3 — interaction with compaction/re-anchor logic.** `tick()` already branches on `content !== snap.content` for compaction detection (`:127-136`) before the stable-content branch; need to confirm the new error check slots into the existing stable-content branch without disturbing that ordering (verified while implementing, not assumed).
- **R4 — `AgentStatus` is reused by `PipelineNodeVM`** (`types.ts:47`). Adding `"throttled"` to the union is additive/backward-compatible (existing `switch`/lookup tables must be checked for exhaustiveness — TypeScript will flag any `Record<AgentStatus, ...>` missing the new key at compile time, which is the safety net here). **(Confirmed by the dueto, finding 3):** `src/sidebar/actions.ts`'s `isRunning` is exactly such a table, and it is a hand-written boolean OR (not a `Record`), so TypeScript's exhaustiveness check does NOT catch it — it must be fixed by hand (folded into Key decisions/Files touched above), and any other `AgentStatus`-keyed lookup found while implementing needs the same manual check.

## Design dueto (SHIP-WITH-CHANGES) — folded

Codex reviewed this plan + `spec.md` plus the cited source/test files. Verdict: **SHIP-WITH-CHANGES**.

- **Finding 1 (required, folded above)** — the original "check `classifyError` globally before `classifyTail`" approach lets a stale error line beat a fresher prompt line further down the pane (two independent full-window scans, not one recency-ordered walk). Fixed: a single unified bottom-up tail walk where the bottom-most matching line wins regardless of category, with same-line ties going to error. New acceptance scenario + required test added.
- **Finding 2 (required, folded above)** — bare `429`/`529`/unqualified "API Error" patterns were too risky. Fixed: replaced with codex's five contextual regexes (require a co-occurring rate/capacity/error word).
- **Finding 3 (required, folded above)** — `src/sidebar/actions.ts`'s `isRunning` predicate is a hand-written boolean check, NOT a `Record<AgentStatus,...>`, so adding `"throttled"` to the `AgentStatus` union does not get caught by TypeScript exhaustiveness checking there; it would have silently stripped `reanchor`/`reinjectContinuity` from a throttled agent. Fixed: `isRunning` updated + a new acceptance criterion + test.
- **Finding 4 (no objection, implementation guidance folded)** — the sustained-state second `onChange` call site is sound, provided it runs inside the same per-agent loop (post-classification) rather than a separate pass over stored snapshots, so a dropped/stopped agent can never fire a stale notify.
- **Finding 5 (suggested, folded above)** — glow-removal alone (same `--ds-warn` fill minus `box-shadow`) was judged too subtle in compact contexts (status chips, a quick scan across rows). Fixed: added a visible darker-amber outline on `.sdot.throttled`, plus `STATUS_LABEL.throttled` so it surfaces correctly in `StatusChips` counts too.
- `src/config/loadConfig.ts:503-571` — confirms `attention.{enabled,silenceSec,patterns}` is the whole current config surface (grounds the "no new config knob for v1" decision).
- Pin `p-6556de` — the originating gap description and its own suggested shape (classify → badge → optional delayed push).
