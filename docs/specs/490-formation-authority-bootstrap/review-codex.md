# SDD 490 — adversarial review

_Reviewer: `codexrev490`. Commissioned 2026-08-05 by `claude`. Review was read-only except for this artifact._

## Verdict

**Revise before planning.** The diagnosis is correct and explicit human adoption is the right authority
boundary, but the draft does not yet specify the actual bootstrap publisher, contradicts its own
delivery acceptance criteria by allowing every spawn to refuse, and names a prompt manifest that can
produce a false green. Multi-workspace scope and the observable product boundary also need to be
settled in the contract rather than deferred to implementation planning.

## Findings

| id | sev | claim and evidence | disposition |
|---|---|---|---|
| C1 | P0 | The draft's non-goal permits the spec to ship while **every** lane refuses at spawn (`spec.md:92-96`), but intent says done means both lanes deliver at spawn (`spec.md:40-42`) and acceptance requires instructions in the composed prompt and Soul `resolved` (`spec.md:60-70`). This is not a clean authority/delivery separation at the product boundary: production hard-codes suppression false (`src/workspace/Workspace.ts:3030-3035`), and the lifecycle refuses before resolving payload when it is false (`src/agents/formation/lifecycleHost.ts:117-120`). Thus the entire proposed change can land and still leave the original user-observable failure unchanged. | Make measured suppression a prerequisite/dependency of the two delivery scenarios (it may remain a separate implementation task), or narrow this spec to authority bootstrap and explicitly defer/remove the claims that lanes reach an agent. It cannot both accept delivery and declare universal refusal shippable. |
| C2 | P0 | The named publisher cannot perform moment zero. Every `HumanLaneTransactionService` mutation first requires an existing `currentVector` (`src/agents/formation/humanLaneTransactions.ts:352-358,427-437,521-537`); it has no bootstrap method. The lower-level store *can* create the initial vector through `replaceVector(... mutation: "bootstrap")`, subject only to its injected `authorizeMutation` callback (`src/agents/formation/authorityStore.ts:331-347,435-475`), while the only production store is deliberately read-only (`src/agents/formation/lifecycleHost.ts:88-96`). Command evidence: `rg -n "new HumanLaneTransactionService|HumanLaneTransactionService\\(" --glob '*.ts'` returns only `test/unit/agentFormationHumanLanes.test.ts:343,523`. Therefore “the only publisher” and “give it a production caller” do not define the required governed bootstrap path, and a second raw-store path could satisfy adoption without the intended custody/audit guarantees. | Require one production bootstrap transaction/port that (a) authenticates a human actor rather than trusting a caller-shaped payload, (b) binds the exact current profile/lane digests, workspace and agent identity, (c) atomically publishes generation 1 plus durable who/when/from-which-bytes audit, and (d) is the only production door to `mutation: "bootstrap"`. Enumerate Interface/Agent/Tachyon × create/restart/recovery callers and expected refusals. Keep `HumanLaneTransactionService` as the post-bootstrap editor if desired, but do not use its mere production reachability as the bootstrap guard. |
| C3 | P1 | “Proved by the prompt manifest” is too weak to prevent a false green. The live `AgentPromptManifest` records persistent instructions as one boolean (`src/agents/promptLayers.ts:75-89`); it records neither formation generation/source nor content digest. The compositor sets that boolean from any non-empty `layers.instructions` and emits those bytes (`src/agents/promptLayers.ts:78,107-118`), while the current spawn path supplies legacy definition instructions (`src/agents/AgentManager.ts:1947-1956`). Separately, the formation snapshot manifest does bind generation and object digests (`src/agents/formation/authorityStore.ts:1003-1014`), but the lifecycle host bypasses snapshot publication, resolves a payload directly, and returns only `payload.soul` (`src/agents/formation/lifecycleHost.ts:126-150`). A test can therefore observe `persistentInstructions: true` without proving the adopted lane supplied the edited bytes. | Name the exact manifest and require it to attest agentId, workspaceId, formation generation/digest, lane source, and the digest of instructions actually composed. Test changed bytes end-to-end through the production restart door, plus a negative control where unrelated/legacy instructions cannot satisfy the assertion. |
| C4 | P1 | Adoption scope is a contract question, not merely UI convenience. A vector is explicitly workspace-bound and validation rejects cross-workspace heads (`src/agents/formation/domain.ts:194-209`); production stores it beneath each workspace root (`src/workspace/Workspace.ts:3020-3025`). Consequently the same canonical `agentId` opened from another checkout/workspace gets another store and remains unadopted, while two windows on the same root share one SQLite authority. The draft leaves “per-agent or per-workspace” open (`spec.md:112-114`) and has no multi-window/reopen/concurrent-adoption scenario, so “a maintainer adopts an existing Saved Agent” has no stable scope. | Ratify adoption as workspace×agent (the current model) or specify a different custody location and migration. Add named tests for two windows on one root, the same agent identity in two workspace roots, concurrent adoption/CAS, and reopen/restart. This is a real gap because it changes the grant's reach and audit identity; bulk UI remains legitimately out of scope. |
| C5 | P1 | The Soul scenario mixes delivery with an obsolete mutation API and is not falsifiable at the product boundary. `createSoulProfile` is specifically the legacy operation that adds inline `soul:` and `assertSoulMutable` rejects canonical profile pointers because those shapes cannot coexist (`src/workspace/Workspace.ts:6480-6510`). Requiring that it “no longer refuses with `soul/canonical-profile-unsupported`” (`spec.md:66-70`) can pass by changing the error code, or can accidentally reopen inline publication, without proving the adopted canonical Soul reached a launched agent. Conversely, a correct implementation may leave that obsolete method refused and expose a distinct governed profile-lane operation. | Replace this assertion with a product-level scenario: adopt canonical Soul, fresh spawn/restart through the production door, and verify the composed prompt/formation manifest binds the adopted Soul digest and authority generation. Separately require Agent Studio's canonical action to route to the governed lane publisher, while the inline mutation path remains impossible. |

## What is solid

- The core diagnosis is supported: the production lifecycle store is read-only and no production
  `HumanLaneTransactionService` exists.
- A human adoption act is consistent with SDD 427's delivered rule that workspace bytes cannot
  activate themselves; no second legitimate **bootstrap** publisher exists today. Evolution and
  selected-memory publishers require human callers but both presuppose an active current vector
  (`src/agents/formation/evolutionTransactions.ts:59-69`,
  `src/agents/formation/memoryTransactions.ts:51-61`), so they do not compete for moment zero.
- Keeping Soul and persistent instructions distinct is settled and was not reopened by this review.
- The unadopted-agent and hand-edited-file negative scenarios are the right fail-closed invariants;
  they become strong once tested through the same production lifecycle door as adoption and launch.
