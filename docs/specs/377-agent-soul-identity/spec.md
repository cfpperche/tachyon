# 377 — agent-soul-identity

_Created 2026-07-13._

**Status:** draft

**Planning task:** `t-60979d`

**Ratification:** pending. The choices marked `R1`–`R6` are recommendations, not yet locked.

**Legacy compatibility baseline:** `23130cea1c1cf8046c1b09ac306de80d92c1bb0e`. This single
feature `BASE_SHA` is immutable for every no-soul parity fixture.

## Intent

Tachyon currently has two persisted prompt inputs for a declared agent:

- `role` is deliberately a reusable operational contract, not a persona;
- `instructions` is free-form persistent specialization.

At launch, those inputs are flattened with Bridge guidance, the Tachyon primer, and sometimes the
current delegation or pipeline task. There is no first-class place to express who an agent is:
its stable voice, values, posture, interaction preferences, and behavioral boundaries. Putting that
material in `instructions` works mechanically, but erases the distinction between identity and work,
makes re-anchoring ambiguous, and prevents Agent Studio from explaining lifecycle and runtime support
honestly.

This feature adds an optional, explicit, per-agent `soul` source backed by a real Markdown file. It
keeps identity separate from role, persistent instructions, Tachyon coordination, repository rules,
and the task of the current execution. A configured soul is loaded from the coordinating workspace,
composed through a typed prompt-layer model, reloaded only at documented lifecycle boundaries, and
never silently ignored or truncated.

Done means two agents can share the same `role` and task specialization while consistently receiving
different identities, with predictable behavior across spawn, restart, resume, fork, re-anchor,
worktrees, and supported runtimes. Existing configurations with no `soul` remain behaviorally and
byte-for-byte compatible at the prompt-composition boundary, including today's legacy placement of a
one-run task before Bridge guidance.

## Vocabulary and trust model

| Layer | Meaning | Persistence | Not this |
|---|---|---|---|
| `soul` | Who the agent is: voice, values, posture, interaction preferences, stable behavioral limits | Explicit workspace-relative Markdown file | Authorization, sandbox policy, memory, or a task |
| `role` | Reusable work contract such as coder, reviewer, tester, or orchestrator | `tachyon.yml` | Persona or rank |
| `instructions` | Persistent specialization for this declared agent | `tachyon.yml` | The objective of one execution |
| current task / brief | Concrete objective, context, constraints, and deliverable for this spawn or Delivery | Typed spawn/delegation metadata | Stable identity |
| Tachyon primer / Bridge guidance | Container protocol, verification discipline, and coordination guidance | Generated by Tachyon | User-authored identity |
| repository guidance | `AGENTS.md`, `CLAUDE.md`, or another runtime-native project convention | Repository/runtime-defined | Per-agent Tachyon soul |

A soul file is trusted workspace configuration, with the same trust posture as `tachyon.yml` and
`AGENTS.md`. It may influence model behavior and therefore must be reviewed like executable
configuration. It is advisory model context, not a security boundary, and cannot grant tools,
permissions, filesystem access, spending authority, or the right to override Tachyon protocol.

Soul is explicitly not confidential input. On current positional-prompt runtimes a short composed
body is visible in process arguments; forcing every soul through a file pointer would reduce that
exposure but also weaken opening delivery to “please read this file”. V1 keeps the existing
inline/long-file transport for reliable parity with `instructions` and makes the exposure a
ratified trust decision. Users needing confidential policy must use a permission/policy/secret
mechanism, not soul.

## Proposed configuration

```yaml
agents:
  security-reviewer:
    cmd: claude
    soul: .tachyon/souls/security-reviewer/SOUL.md
    role: reviewer
    instructions: Focus on authentication and authorization boundaries.
```

`soul` is a single non-empty workspace-relative path written with forward slashes. Agent Studio offers
`.tachyon/souls/<agent>/SOUL.md` as the conventional local/private creation path, but the schema does
not require that directory or basename. Two agents may deliberately reference the same file.

There is no implicit root `SOUL.md` discovery and no inline soul in v1. Omitting `soul` means exactly
today's behavior. Existing `instructions` are not migrated or reinterpreted.

## Prompt model

The conceptual body is:

```text
identity (soul)
→ reusable role contract
→ persistent agent instructions
→ Bridge coordination guidance
→ current execution task
```

The existing Tachyon primer remains the transport envelope at the start, and the before-finishing
gate remains the recency envelope at the end:

```text
Tachyon primer
identity (soul)
role contract
persistent instructions
Bridge guidance
current task / delegation contract
before-finishing gate
```

That canonical body order applies when `soul` is enabled. With no soul, the renderer deliberately
serializes the existing layout byte-for-byte:

```text
Tachyon primer
role contract
persistent instructions + current task (legacy render only)
Bridge guidance
before-finishing gate
```

The current task is still a typed in-memory/persisted layer and is never written back into the
declared `instructions` field. The legacy renderer concatenates it only at the final serialization
boundary. This conditional renderer is the compatibility cost of introducing identity without
rewriting every existing agent prompt.

Order is not provider-level privilege. Most current runtimes receive all Tachyon-owned layers in one
opening user prompt. The runtime/provider system prompt and native project instructions may be placed
at a higher priority by the runtime and remain outside Tachyon's control.

### Conflict rules

| Conflict domain | Winner | Rule |
|---|---|---|
| Provider safety, tool permission, sandbox, or host authorization | Provider/runtime/Tachyon enforcement | A soul never grants authority or weakens a machine gate |
| Repository or container protocol | Repository rule or Tachyon primer/gate | A soul cannot override `AGENTS.md`, verification, ownership, approval, or doorbell protocol |
| Concrete execution objective | Current task | The most specific work contract wins over persistent defaults |
| Persistent operational specialization | `instructions`, then `role` | Preserves spec 216: explicit instructions extend/override the reusable role |
| Voice, tone, values, and interaction style | `soul` unless a higher layer explicitly requires otherwise | Identity supplies stable defaults only inside the authority already granted |

The compositor labels the soul as user-authored identity context and states that it affects behavior
and style only. No prompt wording is treated as enforcement.

## Source resolution and limits

- Resolve `soul` against the coordinating workspace root that owns `tachyon.yml`, never the agent's
  `cwd` or isolated worktree. A delegated branch therefore cannot mutate its own identity merely by
  editing a worktree copy.
- Reject absolute paths, traversal, NULs, parent-directory chains that resolve outside the real
  workspace root, a symlink in the final file component, and non-regular files.
- On POSIX, open with no-follow, validate the open descriptor with `fstat`, and read/hash through
  that descriptor. On Windows, use pre-open `lstat` plus post-open file identity/`fstat` checks;
  a same-user live replacement race that Node cannot portably exclude is outside the trusted
  workspace threat model and must be documented rather than claimed closed.
- Read as strict UTF-8 without line-ending or whitespace normalization. Reject invalid UTF-8,
  embedded NULs, and whitespace-only content. “Character” means a Unicode scalar value.
- Compute SHA-256 over the exact raw source bytes used for the one strict decode; insert that decoded
  text without normalization. CRLF versus LF therefore produces a different payload and digest by
  design.
- Cap one soul at 20,000 Unicode scalar values and 64 KiB of UTF-8 bytes, whichever comes first.
  The character cap aligns with the upstream convention and bounds semantic prompt size; the byte
  cap bounds worst-case I/O/transport. Errors report both measured and allowed values.
- Reject oversize content with an actionable error. Never truncate: the tail may contain values or
  behavioral limits whose removal changes the identity.
- Preserve the existing long-brief file path when the composed prompt crosses its safe inline
  threshold. Derived anchor/brief files use private permissions where the platform supports them.
- A soul is not a secret store. Its resolved body can reach the model provider, runtime transcript,
  short-prompt process arguments, Activity transcript views, and generated files under `.tachyon`.
  `tachyon.yml` and the session ledger retain only the source reference and offer metadata
  (digest/size/time/channel/state), never a second copy of the body. “Offered” means Tachyon handed
  the opening argument/prefill/pointer to the runtime; it is not proof the model/provider consumed it.

## Lifecycle contract

| Event | Soul behavior | When an edited file takes effect |
|---|---|---|
| Fresh spawn / autostart fresh session | Resolve, validate, compose, and record an offered snapshot after launch acceptance | Immediately |
| Restart / crash restart | Resolve again and compose into the new opening prompt; invalid identity is a permanent preflight failure, not an automatic retry loop | On restart |
| Resume existing transcript | Do not duplicate identity; retain the prior offered snapshot | Not until restart, new session, or explicit re-anchor |
| Host Bridge rebind | Reconnect the existing process/session only; no soul injection | Not on rebind |
| Manual or auto re-anchor after compaction | Resolve current source and generate a full identity + contract anchor before offering the pointer/primer; show any digest transition | On successful re-anchor |
| Native transcript fork | Do not duplicate identity in the fork opening; copy source reference and offered snapshot | Original identity in transcript; current file on later restart/re-anchor |
| Bound Delivery execution using `declared_agent` | Inherit the declared principal's soul reference; keep the Delivery task in the task layer | On fresh Delivery execution/restart |
| Pipeline or schedule using a declared agent | Inherit that agent's soul; pipeline/schedule objective remains the task layer | On each fresh execution |
| Ad-hoc `cmd` spawn | No soul argument in v1; identity is not inherited from the parent | Not applicable |
| Declared subagent | Uses its own configured soul; a parent's identity is never contagious | On the child's fresh spawn/restart |
| Agent rename | Preserve the explicit reference; never move a user-authored file silently | Unchanged until the user edits the reference |
| Isolated worktree | Always read from the coordinator workspace root | Worktree edits do not take effect before integration |

A configured soul that cannot be resolved blocks fresh spawn/restart for that agent. Re-anchor fails
visibly and leaves the existing conversation running; it must not inject a partial contract. Resume
and rebind remain available because they do not require re-reading the source.

Identity preflight must run before an agent-specific worktree/stub, Delivery lease, token/harness,
or pane is created/replaced. A failed restart leaves the currently running process untouched. A
soul-aware re-anchor writes its generated anchor in the coordinator workspace and injects a
shell-safe absolute pointer, so an agent running in another worktree can still read it.

Fail-closed availability is intentional and has no automatic “start without identity” bypass:

- byte-cap classification precedes change detection: a descriptor size above 64 KiB or either
  bounded read observing a 64 KiB + 1 sentinel byte returns deterministic `too-many-bytes`
  immediately, with no retry. `source-changed-during-read` is considered only when both observed
  payloads are within the cap;
- deterministic validation/capability failures (`path-invalid`, `missing`, `outside-workspace`,
  `final-symlink`, `not-regular`, `permission-denied`, `invalid-utf8`, `empty`,
  `too-many-chars`, `too-many-bytes`, or `runtime-unsupported`) latch immediately and wait for
  repair followed by manual restart;
- only transient filesystem/resource failures (`EIO`, `EBUSY`, `EMFILE`, `ENFILE`, or
  `source-changed-during-read`) use bounded retries after 2s, 4s, and 8s, then latch/fail that
  execution; every unrecognized error defaults to deterministic/fail-closed and never gains an
  implicit retry path;
- `source-changed-during-read` means two bounded reads from explicit offset zero on the same open
  handle differed, or descriptor size/mtime/ctime changed across those reads. An atomic rename does
  not invalidate an already-open descriptor; a bare `ENOENT` while opening remains deterministic
  `missing`;
- a human fresh spawn/restart uses the same non-blocking bounded schedule for transient errors. A
  restart does not replace the current process unless preflight succeeds; after exhaustion the UI
  surfaces/latches the failure, and both deterministic and transient-exhaustion cases preserve the
  live process;
- a scheduled/pipeline/Delivery execution fails that execution with the soul error before acquiring
  agent-specific resources; a later scheduled execution may preflight again, but no tight loop runs;
- a human can repair the file or explicitly remove `soul` from config, which is the auditable
  opt-out.

If compaction triggered a re-anchor and that re-anchor fails, the session is marked
`identity-degraded` in durable metadata/Activity and requests human attention. Tachyon does not kill
or freeze the conversation, but it suppresses automatic re-anchor retries until a human retries
re-anchor/restart after repairing the source. V1 adds no background soul watcher. A successful
re-anchor from digest A to B emits a visible transition; it is never a silent live-identity switch.

## Runtime contract

Tachyon promises a durable identity input, not a universally native system-prompt slot.

| Runtime family | Current Tachyon channel | v1 soul status |
|---|---|---|
| Claude | Opening positional prompt | Supported as `offered/startup-argument` through typed prompt composition |
| Codex | Opening positional prompt | Supported as `offered/startup-argument`; native `AGENTS.md` remains independent repository guidance |
| Gemini | `-i` opening prompt | Supported as `offered/startup-argument` |
| Antigravity / `agy` | `--prompt-interactive` | Supported as `offered/startup-argument` |
| OpenCode | `--prompt` TUI prefill | Supported as `offered/prefill`; user submission/model consumption is not guaranteed |
| Grok | Opening positional prompt | Supported as `offered/startup-argument` |
| Hermes | Native `$HERMES_HOME/SOUL.md`, but no Tachyon-owned per-agent Hermes home/profile today | Fail closed when Tachyon `soul` is configured in phase 1; do not overwrite or compose with the user's global/profile soul |
| Qwen, Aider, Goose, Amp, Cursor Agent, Copilot, Pi, Verboo, unknown CLIs | No verified automatic opening-prompt adapter in Tachyon | Fail closed when `soul` is configured; never store-and-silently-drop |

Legacy `instructions` retain their current compatibility behavior, including a non-blocking warning
on runtimes that cannot deliver them. `soul` is stricter because silently dropping identity would
misrepresent the feature.

Runtime classification uses Tachyon's existing syntactic `resolveBinary` rule: direct binaries plus
`env` and `npx`/`bunx`/`pnpx` launchers are recognized by basename. Arbitrary shell-script aliases,
`bash -lc` wrappers, and renamed binaries are unsupported for soul in v1 and fail with a diagnostic
that asks for a direct supported command. Basename selection chooses an adapter; it is not a binary
provenance guarantee. An explicit runtime override is a future runtime-parity feature, not guessed
here.

Hermes native support is a follow-on adapter gate, not a file-copy shortcut. It requires a proven
per-agent `HERMES_HOME` or Hermes profile lifecycle that preserves auth/config, isolates concurrent
agents, and never mutates `~/.hermes/SOUL.md`. Until that proof exists, Tachyon documents native
Hermes SOUL as externally managed.

## Acceptance criteria

- [ ] **Scenario: explicit per-agent soul round-trips**
  - **Given** an agent with a workspace-relative `soul` path
  - **When** config is parsed, edited in Agent Studio, and written back
  - **Then** the forward-slash string is preserved as a single reference; `terminals:` entries and
    `kind: terminal` entries reject `soul`; empty strings, arrays, and non-strings are rejected
- [ ] **Scenario: existing agents are unchanged**
  - **Given** any valid pre-feature agent with no `soul`, the immutable baseline
    `23130cea1c1cf8046c1b09ac306de80d92c1bb0e`, and a parity-fixture manifest pinned to that exact SHA
  - **When** fresh spawn, restart, no-soul re-anchor, bound Delivery/pipeline task composition, and
    the pre-existing no-soul short/long-brief transport are exercised
  - **Then** fixtures captured before any compositor/task-layer change prove byte-identical prompts,
    role docs, commands, and brief files, including legacy role → persistent instructions + current
    task → Bridge guidance placement; CI fails unless the manifest and every parity fixture carry the
    exact pinned SHA, and expected bytes are never regenerated from the new renderer
  - **And** BASE_SHA command/send-key fixtures prove human resume, host rebind, and native fork keep
    their exact legacy outputs; call spies additionally prove none invokes the legacy/soul prompt
    serializers, soul resolver, or long-brief compositor
- [ ] **Scenario: same role, different identities**
  - **Given** two agents with the same `role` and `instructions` but different soul files
  - **When** both start
  - **Then** both receive the same operational contract and their own distinct labeled identity body
- [ ] **Scenario: deterministic composition**
  - **Given** `soul` and all supported layers are present
  - **When** the opening prompt is rendered
  - **Then** section order is primer → soul → role → instructions → Bridge guidance → current task →
    before-finishing; current task remains typed and never mutates declared `instructions`
- [ ] **Scenario: source validation fails closed**
  - **Given** a soul path that is missing, outside the workspace, a symlink/special file, invalid UTF-8, empty, or over a limit
  - **When** a fresh spawn, restart, or re-anchor resolves it
  - **Then** delivery stops with a specific actionable error, no partial identity is injected, and
    no new agent-specific worktree/lease/pane side effect is left behind
  - **And** a stable file above 64 KiB is classified `too-many-bytes` before change detection and
    schedules zero retries
- [ ] **Scenario: resume preserves transcript semantics**
  - **Given** a session launched with soul digest A and a file later edited to digest B
  - **When** the session resumes or is host-rebound
  - **Then** Tachyon does not inject B, metadata still reports A as previously offered, and the
    transcript is resumed normally
- [ ] **Scenario: restart and re-anchor refresh identity**
  - **Given** that same edited file
  - **When** the agent restarts or is explicitly re-anchored
  - **Then** B is resolved, offered through the correct boundary, and recorded with its channel/state;
    a worktree agent receives a readable shell-safe pointer to the coordinator anchor and an A→B
    transition is visible
- [ ] **Scenario: failed compaction re-anchor is visible**
  - **Given** a compacted session and a soul source that cannot be resolved
  - **When** auto/manual re-anchor fails
  - **Then** no partial anchor is injected, the session is marked `identity-degraded`, human attention
    is latched, and automatic retries pause until a human retries after source repair
- [ ] **Scenario: fork does not duplicate identity**
  - **Given** a live fork-capable session with a soul
  - **When** Tachyon creates a native transcript fork
  - **Then** the fork inherits transcript context and soul metadata without a second opening soul block
- [ ] **Scenario: declared principal identity survives delegation**
  - **Given** a bound Delivery/pipeline/schedule execution selected from a soul-enabled declared agent
  - **When** its task is composed
  - **Then** the declared soul is inherited and the current objective remains a separate, last operational layer
- [ ] **Scenario: unsupported runtime is honest**
  - **Given** an agent whose runtime has no verified soul delivery adapter
  - **When** `soul` is configured and a fresh start is attempted
  - **Then** Agent Studio/config diagnostics name the unsupported runtime and start fails instead of silently omitting identity
- [ ] **Scenario: wrapped commands have deterministic support**
  - **Given** direct, `env`/package-launcher, shell-wrapper, and renamed-binary commands
  - **When** soul capability is classified
  - **Then** direct/recognized launchers select the expected adapter and arbitrary wrappers fail with
    an actionable direct-command diagnostic
- [ ] **Scenario: unattended identity failure does not loop or degrade**
  - **Given** an invalid soul during crash restart, autostart, schedule, pipeline, or Delivery start
  - **When** preflight runs
  - **Then** no identity-less fallback starts; enumerated and unknown deterministic errors latch
    immediately, only enumerated transient errors retry after 2s/4s/8s before latching/failing, and
    the execution records a specific failure before agent-specific resources are acquired
- [ ] **Scenario: transient human restart preserves the live process**
  - **Given** a running agent and a soul read that repeatedly returns an enumerated transient error
  - **When** a human requests restart
  - **Then** retries occur after 2s/4s/8s without replacing the pane/process; exhaustion is surfaced
    and latched, while a successful retry replaces the process only after preflight completes
- [ ] **Scenario: ledger and generated-artifact privacy**
  - **Given** a successful soul offer
  - **When** session state and generated files are inspected
  - **Then** ledger metadata contains reference/digest/size/time/channel/`offered` state but not body,
    derived files are private where supported and gitignored, and documentation states
    transcript/argv/provider exposure
- [ ] **Scenario: derived identity retention is bounded**
  - **Given** brief/anchor files for a resumable or running agent
  - **When** it stops, resumes, restarts, is dismissed, or its declared entry is deleted
  - **Then** files are retained while transcript pointers may still need them, overwritten on refresh,
    and removed on permanent identity cleanup without orphaned body copies
- [ ] **Scenario: Agent Studio explains the model**
  - **Given** an agent opened in Agent Studio
  - **When** the user selects, creates, previews, opens, clears, or renames around a soul
  - **Then** identity is visually separate from Role and Persistent instructions, lifecycle/runtime status is explicit, file operations are keyboard accessible, and no file is silently moved
- [ ] **Scenario: long composed prompt remains lossless**
  - **Given** a valid soul that pushes the full body beyond the inline threshold
  - **When** the agent starts
  - **Then** the existing brief-file transport carries every layer in order without truncation and the pane receives the bounded pointer envelope
- [ ] Unit, integration, browser-surface, lifecycle, and compatibility tests cover the scenarios above.
- [ ] Headless dogfood launches two same-role agents through capture runtimes with different souls and proves distinct prompts without paid inference.
- [ ] Runtime parity and user documentation distinguish Tachyon prompt composition, runtime-native files, and unsupported delivery.

## Non-goals

- Memory, user profile, `USER.md`, long-term learning, or automatic identity mutation.
- A global/default soul, soul inheritance tree, named soul registry, or runtime-profile DSL in v1.
- Implicit discovery of a repository-root `SOUL.md`.
- Inline soul bodies, arrays of soul files, remote URLs, templates downloaded from a directory, or
  arbitrary includes.
- A new `soul` argument on generic Bridge ad-hoc spawns in v1.
- Arbitrary shell-wrapper runtime inference or an explicit `runtime:` override in v1.
- Treating a soul as an authorization, policy, compliance, or secret-management mechanism.
- Guaranteeing that every provider receives soul at native system-prompt priority.
- Silently overwriting or cloning a user's Hermes profile/home.
- Making model behavior deterministic; verification covers delivery and composition, not subjective
  obedience to personality prose.

## Maintainer ratification

- **R1 — configuration (recommended):** one explicit per-agent file reference; no auto-discovery,
  inline body, global default, or profile inheritance in v1.
- **R2 — runtime rollout (recommended):** phase 1 supports only syntactically recognized verified
  opening-prompt adapters, fails closed for wrappers/native-external/unsupported runtimes, and defers
  Hermes native per-profile support to a separately proven home/profile adapter.
- **R3 — lifecycle (recommended):** refresh on fresh spawn, restart, and re-anchor; never duplicate on
  resume, rebind, or native fork.
- **R4 — limits/trust/availability (recommended):** 20,000 Unicode scalar values plus 64 KiB raw
  byte ceiling, exact-byte digest/no truncation, trusted-workspace posture, current inline/long-file
  transport with explicit argv exposure, no automatic identity-less fallback, and visible
  `identity-degraded` state after failed compaction recovery.
- **R5 — Studio ownership (recommended):** Agent Studio stores a path and provides create/select/open/
  preview actions; editing remains in the real Markdown editor, not an inline textarea.
- **R6 — typed composition (recommended):** separate current-task metadata from persistent
  `instructions`, but retain a golden-pinned legacy serializer for no-soul agents; only soul-enabled
  prompts adopt the new canonical task-after-Bridge section order.
