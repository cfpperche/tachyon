# Adversarial review — SDD 488 / Integrated Browser Design Mode

Reviewer: `codex`  
Date: 2026-08-04  
Scope: `tachyon/grok`, including committed prototype and current uncommitted changes. Review only; no feature implementation or merge.

## Verdict

**Rework before merge discussion.** The prototype proves that VS Code's Integrated Browser can host a credible pick/chat loop, and the SDD is appropriately `draft`, but this tree is not safe or reliable enough for dogfood outside a tightly controlled fixture. The largest problem is an authority collapse: the injected page can invoke a host CDP binding, every authenticated agent receives unrestricted page-context `eval`/click, and chat replies can self-declare another agent's name. The two-bridge lifecycle also has destructive catalog refresh, ambiguous multi-instance discovery, and no turn correlation. These are v1 properties, not optional GA hardening; deferring them to F6/F9 would ratify the wrong contract.

## Spec vs code drift

1. **Security is wrongly deferred.** F6 calls eval/click/token/Trusted Types a pre-GA checklist (`spec.md:196`), but these surfaces are already required to deliver the v1 loop and are reachable by every authenticated agent. They must be v1 acceptance criteria.
2. **F9 is already a v1 correctness issue.** Parent/child workspace matching and multiple matching instance files are current discovery behavior (`client.ts:71-97`), not a theoretical later multi-root enhancement.
3. **“Refresh live sessions” is not what the code does.** It closes sessions (`Bridge.ts:177-184`). The subsequent announcement cannot reach those closed sessions, and always-registration means browser lifecycle does not alter the catalog.
4. **Single-agent v1 conflicts with group-chat presentation.** The code visibly promises a group thread while routing one selected saved agent; this is not merely future-ready styling.
5. **Running-agent acceptance is unimplemented.** The roster intentionally returns saved agents without checking `running`; chat appends before delivery validation. `tasks.md:21-23` correctly remains unchecked, but `plan.md:27-33` describes the prototype as already having the selector/flow more strongly than the code warrants.
6. **Durability/virtualization is overclaimed.** The UI caps DOM nodes, but storage operations read the whole JSONL for append, tail, and older windows. There is no crash or concurrent-writer contract.
7. **Markers are still first-class in prompts.** The SDD calls them emergency fallback, while every generated prompt explicitly instructs their use.
8. **Tasks honesty is mixed but mostly acceptable.** The unchecked Phase 1/2 boxes correctly acknowledge missing product reliability. The checked refresh items (`tasks.md:13-14`) are mechanically wired but semantically misleading because the implementation disconnects sessions rather than refreshing them. The checked always-register item lacks its required tests and threat/authority contract.
9. **Dogfood opt-out is reasonable for full visual behavior but too broad as cover.** HTTP auth, binding validation, lifecycle, tool registration, offline envelopes, turn routing, and hostile-page behavior are meaningfully headless and should not wait for an Extension Development Host.
10. **Status `draft` is appropriate.** The amount of prototype code does not justify `in-progress` until Q1-Q5 and the security/authority contract are ratified.

## Top 5 blockers before any merge discussion

1. **Close the page-to-host binding boundary (C-01).** A navigated page must not be able to send host commands or agent prompts merely because Design Mode is injected.
2. **Define and enforce browser mutation authority (C-03/C-08).** Arbitrary eval/click against potentially authenticated pages cannot ship as an always-visible, unapproved agent capability.
3. **Bind chat replies to authenticated caller + turn (C-02/C-06).** Eliminate speaker spoofing, late-reply corruption, and agent-switch races.
4. **Replace destructive tool refresh and make two-bridge ownership deterministic (C-04/C-05/C-09).** Browser start/stop must not drop unrelated MCP sessions or attach to an arbitrary same-root instance.
5. **Prove production-door behavior (C-07/C-13).** Add concurrent JSONL/lifecycle/auth/registration/reply tests and complete the human runtime matrix; the current 31 green tests primarily validate pure formatting and source structure.

## What is solid

- The three-browser product matrix is clear and worth keeping; Design Mode, Companion, and agent-browser have distinct owners/jobs.
- `draft` plus an explicit no-merge rule is honest and appropriate.
- The loopback listener, random token, `0700` directory, and `0600` instance file are sensible transport-level hygiene (`manager.ts:113-127,740-765`).
- Always-registering independently of momentary online state fixes the catalog freeze failure mode; the remaining question is which capability subset should always register.
- Pick payloads are bounded: text 240 chars, HTML 4,000 chars, and computed styles use an allowlist (`pick.ts:31-55,103-144`).
- Chat rendering uses `textContent` for message bodies, avoiding direct HTML rendering of agent/user content (`designModeInject.ts:1010-1024`).
- The SDD records observed failures instead of hiding them, and `tasks.md` leaves most productization work unchecked.
- Focused tests are fast and green: `designModeChat`, `ideBrowserClient`, `designModePick`, and `designModeInject` passed 31/31 on 2026-08-04. That is useful groundwork, though not ship evidence.

## Suggested acceptance-criteria corrections

Add these to v1 rather than F6/F9:

- A page script cannot invoke or forge any Design Mode host action; prove with a hostile fixture page.
- `design_mode_chat_reply` attributes the authenticated Bridge caller and rejects a claimed alternate speaker.
- Every chat send has a turn id; late/wrong-agent replies cannot complete another turn.
- Read, navigate, click, and eval have an explicit principal/origin/approval policy; eval is absent unless that policy is ratified.
- Two live VS Code windows for related roots resolve deterministically or refuse with an actionable ambiguity error.
- Starting/stopping Integrated Browser does not terminate unrelated in-flight MCP operations.
- Concurrent chat appends produce unique ordered ids or one writer is mechanically enforced.
- Offline tools remain listed without requiring any browser-lifecycle catalog refresh.
