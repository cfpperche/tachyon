## Intent

Let the `visual-qa` skill turn a NAMED SURFACE into a route URL by consuming the spec-278 route catalog, so
`/visual-qa agent-studio --anchor "…"` (or "the Agent Studio tabs") resolves automatically. The human still declares
the catalog's LOCATION (a trusted project artifact, like `config.routes`); the skill + agent do the name→URL mapping.

**Discipline unchanged.** The anchor is still required (invocation or config, else `unable_to_judge`). Discovery only
removes the "ask the human for the URL" step when a catalog is declared and the name matches an entry.

## What exists (grounding)

- The catalog (`scripts/webview-preview/routes.json`) is GENERATED by `buildCatalog()` (spec 278), kept in sync by a
  smoke test, and served by the harness (`serve.mjs` serves the repo root → `/scripts/webview-preview/routes.json`).
- Each entry: `{ view, fixture, url, frame, tags }`. `url` is a RELATIVE harness path
  (`/scripts/webview-preview/index.html?view=<v>&fixture=<f>`); it needs a base host (the serve URL) to be reachable.
- The skill's spec-277 resolution already has a precedence table (invocation > config baseline > fallback) + a
  runtime-readiness check; discovery slots a new tier into it.

## Design

### 1. Config — declare WHERE the catalog is (`config/schema.json`)

Add an optional `catalog` object (the human declares the trusted artifact's location; absent → no discovery, exactly
today's behavior):
- `path` — workspace-relative path to the generated catalog JSON (e.g. `scripts/webview-preview/routes.json`).
- `base` — the URL host the relative catalog URLs resolve against (e.g. `http://localhost:5174`); this is where
  `config.setup` serves the harness.

### 2. Catalog enrichment — a friendlier match key (spec 278 `buildCatalog`)

Add an optional `title` (human label) and `aliases` (extra exact-match keys) per view to the route table (`ROUTES`)
and emit them in the catalog (`{ view, fixture, url, frame, tags, title?, aliases? }`) so the deterministic match
resolves "Agent Studio" → `agent-studio` on a human-readable label / alias, not just the kebab id. Minimal,
back-compatible (absent → match on `view`).

### 3. Skill — the catalog-resolution algorithm (`SKILL.md`, executable, not prose)

When the target is a NAMED SURFACE (not a direct URL), the skill runs this ORDERED checklist (folded from Codex):

1. **Run `config.setup` first** (serve the harness) so `config.catalog.base` is reachable. If setup fails / base is
   unreachable → `unable_to_capture` (a capture/setup failure, NOT a visual `fail`, NOT `unable_to_judge`), recording
   the candidate it was about to resolve. Never proceed to judge against an unreachable base.
2. **Resolve the view+fixture — DETERMINISTIC FIRST:**
   a. parse a `view:fixture` syntax (`agent-studio:edit-agent`) if present;
   b. exact `view` id match → that view; else exact `title` match; else an explicit `alias` match;
   c. ONLY if none match deterministically: a semantic/tag match (read the catalog, pick the best view) — but when
      >1 plausible view exists (e.g. `pin` → pin-studio + pin-preview), ASK rather than guess. Tags alone never decide.
3. **Pick the fixture:** the named fixture (`view:fixture`), else the view's `default`; if the phrase implies a STATE,
   LIST the view's fixtures and ask/pick the matching one (the defect may live in a non-default fixture).
4. **Join the URL (relative-only):** `resolved_url = base (trailing-/-trimmed) + entry.url (leading-/-kept, query
   preserved)`. The catalog `url` MUST be relative; an absolute catalog URL is rejected (absolute targets go through
   `config.routes`, not catalog data).
5. **Open + verify the surface (anti-stale):** after opening `resolved_url`, confirm the rendered page declares the
   expected `view`/`fixture` via the harness DOM marker (design #5); on a mismatch → `unable_to_capture` + ask (a stale
   catalog rendering a DIFFERENT surface must not be judged as the named one).
6. **Record provenance in the verdict `data`:** `resolution_source: "config.routes" | "catalog" | "human"`, `view`,
   `fixture`, `catalog_path`, `catalog_base`, `resolved_url`, `catalog_hash` (so a reviewer sees exactly what was QA'd).

This tier is ADDITIVE: a declared catalog with a match resolves automatically; no catalog / no match → the spec-277
`config.routes`-then-ask path, unchanged. The anchor stays mandatory throughout — no anchor → `unable_to_judge`, never
"discovery failed".

### 4. Harness view marker (anti-stale, spec-278 `preview.ts`)

`preview.ts` sets a DOM marker on render — `document.body.dataset.previewView = view; …previewFixture = fixture` — so the
skill (step 5) can confirm the resolved URL actually rendered the named surface (catches a stale-but-valid catalog).

### 5. Wire Tachyon's own config

Point Tachyon's `visual-qa` config (`.tachyon/plugins/visual-qa/config/visual-qa.json`) at the catalog
(`path: scripts/webview-preview/routes.json`, `base: http://localhost:5174`) so `/visual-qa agent-studio` works against
Tachyon's own UI via the harness.

## Acceptance criteria

- [ ] **Config:** `config/schema.json` gains an optional `catalog: { path, base }`; an empty/absent catalog leaves
  today's behavior unchanged (named surface → config.routes, else ask).
- [ ] **Catalog title:** `buildCatalog()` emits an optional `title` per entry; the smoke test + committed routes.json
  stay in sync; back-compatible.
- [ ] **Resolution algorithm (executable, deterministic-first):** the SKILL.md carries the ordered checklist — setup
  first → deterministic match (view/title/alias/`view:fixture`) → semantic only on no-match with ask-on-ambiguity →
  relative-only URL join → post-open view-marker verify → provenance recorded. Not loose prose.
- [ ] **Failure modes distinct:** setup-fail/base-unreachable → `unable_to_capture`; stale-but-valid (marker mismatch)
  → `unable_to_capture`+ask; no anchor → `unable_to_judge` (unchanged). Discovery never masks the anchor discipline.
- [ ] **Harness view marker:** `preview.ts` sets `body.dataset.previewView`/`previewFixture`; the skill verifies it
  post-open (a render check, not just a URL).
- [ ] **Provenance recorded:** the verdict `data` carries `resolution_source`/`view`/`fixture`/`catalog_path`/
  `catalog_base`/`resolved_url`/`catalog_hash`.
- [ ] **Tachyon wired + PROVEN with the right fixture:** Tachyon's visual-qa config declares the catalog; a dogfood
  resolves `agent-studio` → the catalog URL → a live render, AND states WHICH fixture (default vs edit-agent) shows the
  owner's button inconsistency — baked into the proof.
- [ ] **No regression:** plugin engine-validates (loadPlugin/ajv); Tachyon full suite + typecheck/build/engine-boundary
  green (only `buildCatalog`/routes.json/`preview.ts` marker change Tachyon-side).

## Open questions — RESOLVED (Codex dueto 2026-06-28, leans folded)

- **OQ1 — match mechanism:** **deterministic-first, semantic-second.** Exact `view` / `title` / explicit `alias` /
  `view:fixture` beats agent vibes; a semantic/tag match is allowed ONLY on no deterministic hit, and asks on ambiguity
  (tags alone never decide).
- **OQ2 — fixture selection:** **`default` for an exact view name; `view:fixture` for a non-default; LIST fixtures when
  the phrase implies a state.** The dogfood must prove whether the button pain is in `agent-studio/default` or
  `/edit-agent` and bake that in.
- **OQ3 — generic vs Tachyon:** **a generic catalog CONTRACT, Tachyon-first implementation.** No catalog ⇒ no
  resolution path (today's config.routes/ask), unchanged; don't imply arbitrary-app auto-discovery.
- **OQ4 — trust + base:** **same trust as `config.routes`**, but catalog URLs are constrained to RELATIVE paths
  (absolute targets must go through `config.routes`, not catalog data) — defense-in-depth, not a security input.
- **OQ5 — staleness:** **minimal runtime detection, not just ask-on-miss** — the harness DOM view-marker (verified
  post-open) catches stale-but-valid; the catalog hash is recorded in evidence. CI sync alone isn't enough for local
  dogfood trust.

## Non-goals

- Changing the anchor discipline, the capture/judge/attach flow, or the spec-277 precedence for URL/anchor inputs.
- A registry/index server, fuzzy-search infra, or embeddings — the catalog is a flat JSON the agent reads.
- Auto-generating named surfaces for arbitrary web apps (no catalog → the config.routes/ask path, unchanged).
- The all-views harness itself (spec 278, shipped) or any new Tachyon webview.
