# Post-0.56.110 Install Incident

Reporter: out-of-Tachyon session  
Date: 2026-07-28  
Host: WSL2 / VS Code Remote (`wsl+ubuntu`)  
Workspace: `b349073a` (`/home/goat/tachyon`)

## Impact

Installing Tachyon 0.56.110 caused the VS Code extension host to enter a
repeatable out-of-memory crash loop. Rolling the extension back to 0.56.109
did not recover the workspace because the persistent 0.56.110 engine survived
the reinstall. Recovery required manually terminating the engine and reloading
VS Code on 0.56.109.

0.56.110 is therefore **do not install** until the incident blockers below are
fixed and an upgrade/rollback release is verified across versions.

## Timeline

- Jul 27 19:54 — extension host starts on 0.56.109 and runs for about 17 hours.
- Jul 28 13:03:41 — 0.56.110 installation begins.
- 13:03:50 — supervisor commits the 0.56.109 → 0.56.110 engine handover with

- 13:05–13:29 — four extension reinstall attempts alternate between 0.56.110
  and 0.56.109 while the 0.56.110 engine process remains alive.
- 13:37 — manual engine termination followed by reload restores 0.56.109.

## D1 — Wire-format break without a protocol bump (P0)

Both 0.56.109 and 0.56.110 declare engine protocol `{min:3,max:3}`. Negotiation
therefore succeeds even though a 0.56.109 client cannot decode a 0.56.110
response:

`src/engine-service/controlClient.ts:433`

> engine control response violates the protocol

The bounded client read and fail-closed response are correct. The defect is the
unchanged protocol version and the absence of an N↔N±1 compatibility gate.

Required outcome:

- incompatible wire formats must not negotiate successfully;
- version skew must produce an explicit, actionable refusal;
- the release gate must exercise the current client/engine against the previous
  release in both relevant directions.

## D2 — Extension rollback leaves the newer engine running (P0)

Engine PID 1719864 survived four extension reinstall/rollback attempts.
Downgrading the extension therefore continued to pair a 0.56.109 client with a
0.56.110 engine. Because the extension host was crashing, the normal governed
restart/stop commands were unavailable.

Required outcome:

- version skew must be reported on a surface that remains readable when Control
  cannot load;
- installing or downgrading must restage/restart an incompatible engine, or
  refuse with an exact recovery action;
- a governed recovery path must remain available when the extension host or
  Control surface is unhealthy.

## D3 — Extension-host OOM on 0.56.110 (P0, root cause unknown)

The V8 heap grows to approximately 4 GB in about 22 seconds after Tachyon
activation and aborts with `Reached heap limit`. The final native allocation is
`v8::String::NewFromTwoByte`, consistent with an unbounded/repeated string read
or concatenation.

The incident occurred with a 0.56.110 client and a 0.56.110 engine. It is not
yet known whether D3 is independent from D1 or a downstream lifecycle effect.

Already ruled out; do not restart these investigations without contrary
evidence:

- bounded control client frames;
- bounded engine event journal;
- bounded Codex rollout evidence reader;
- bounded resume resolvers;
- per-chunk-capped Grok/OpenCode launch preflights;
- the 1.8 KB execution graph ledger;
- corrupted build artifacts;
- the webview READY-handshake change.

Next diagnostic is a controlled reproduction with a near-heap-limit snapshot
and a pre-agreed recovery path. Re-entering the crash loop requires human
authorization.

Closure rule: disappearance after client/engine realignment is only
“not currently reproducible.” D3 must not be closed without either a proven
root cause plus regression coverage, or an instrumented reproduction matrix
that demonstrates D1 was the cause.

## D4 — SDD 472 invalidated existing Codex config without migration (P1)

Existing global Codex configuration:

```toml
approval_policy = "never"
sandbox_mode = "danger-full-access"
```

became refused unless each canonical agent explicitly authorizes the values.
The fail-closed intent and refusal text are valid, but the upgrade invalidated a
previously working fleet without migration, grandfathering, or an upgrade
workflow.

Required outcome: preserve the security boundary while providing an explicit,
reviewable migration/authorization flow before an existing workspace becomes
invalid.

## O1 — Stale webview chunks in the package

The package contains 134 `cockpit-App-*.js` chunks (9.7 MB), while only 24 are
referenced by `cockpit.js`. This is not causal to the incident, but packaging
must prune unreferenced chunks to reduce VSIX size and artifact-diff noise.

## Release policy for this incident

- Freeze feature landing into the recovery release.
- Do not reinstall 0.56.110.
- Do not publish to Marketplace.
- The next local VSIX is eligible only after D1, D2, and D4 are fixed and the
  cross-version upgrade/rollback gate passes.
- D3 reproduction is a separate controlled operation requiring human approval;
  a non-reproduction does not silently close it.
- O1 is non-blocking for the recovery release.
