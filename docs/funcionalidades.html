Núcleo — processos vivos em terminais nativos

Agentes como sessões tmux

Cada agente/terminal é uma sessão tmux num servidor dedicado (tmux -L tachyon), exibida como terminal nativo do editor. Fechar a aba nunca mata o processo; reiniciar o VS Code só re-anexa. O engine fala com o tmux por um cliente control-mode persistente — mudanças de ciclo de vida chegam como eventos (~1s), com fallback transparente para subprocessos one-shot se o cliente cair. Qualquer agente spawnado pelo Tachyon recebe o Bridge injetado (aditivo, nunca substitui a config do usuário) e um token de identidade próprio. maxAgents (padrão 8) impede fork-bomb de agentes spawnando agentes.

Agents vs terminals — taxonomia kind

Declare CLIs de IA em agents: e servidores/shells/builds em terminals:. Por baixo é um único conjunto gerenciado com tag de kind: ambos ganham sessão, aba, detecção de crash, restart por watch de arquivos, worktree e re-attach. O kind guia o agrupamento na sidebar e o default de atenção (agentes: ligado; terminais: desligado).

Comunicação entre agentes

Sem message bus: três canais concretos mediados pelo Bridge. (1) Os próprios terminais — read_output captura o pane de outro agente, write_input digita nele. (2) Sincronização — wait_for_agent bloqueia até idle/needs-input/dead (long-poll orientado a eventos, o primitivo da delegação: spawn → wait → read → kill); wait_for_output/wait_for_lease esperam por saída/lease específicos. (3) Memória compartilhada — pins, handoff, tasks. Não existe push para um agente em execução (MCP é request/response); um pai só descobre que o filho terminou fazendo uma chamada.

Detecção de atenção — "este agente precisa de você"

needs-input (forte): o fim do pane bate num prompt reconhecível ([y/n], senha, seletor numerado…) e está estável → sino amarelo, badge no ícone ⚡ e toast único com botão Open. idle (fraco): sem saída por silenceSec (8s) e CPU da subárvore plana (CPU ocupada = pensando, suprime) → ícone esmaecido, nunca toast. O engine classifica cada pane em working · idle · needs-input · throttled (rate-limit notifica só após 45s estável) com a flag stalled após 5 min sem saída, e um "working" congelado >20 min é rebaixado — nada fica preso em "ocupado" para sempre. Configurável por entrada (silenceSec, patterns); estado exposto a outros agentes via list_agents.

Ciclo de crash — exit code, postmortem, auto-restart

Processo morre sozinho → o dead pane é preservado (stack trace visível) e a sidebar mostra crashed — exit N com ações ↻/■. Kills intencionais ficam silenciosos (distinção estrutural). restart: on-crash religa só exits ≠ 0, com backoff 2s/4s/8s e guarda de crash-loop (3 restarts/min → desiste, mantém o postmortem, avisa).

Activity — trilha durável de atividade por agente

Normalizadores por runtime (claude, codex, grok, opencode) mapeiam os transcripts em disco para um vocabulário de eventos agnóstico de runtime, gravado em arquivo append-only por agente em .tachyon/activity/ — costurando sessões através de /clear/resume, com atribuição correta quando vários claude compartilham a mesma pasta (ledger de donos de sessão via hook SessionStart). Alimenta o painel Activity, o compartilhamento de atividade entre agentes e o agregado de uso de tokens por runtime (status bar $(pulse) Runtime / view Runtime Ops). Sessão ambígua → não escreve nada, nunca chuta; evento não mapeado degrada para raw, nunca lança.

Resume de sessão — sobrevive a reboot, não só restart

Restart do VS Code: o tmux segue vivo, Tachyon re-anexa. Reboot/wsl --shutdown/OOM: Tachyon regrava cada agente com a conversa via o resume nativo do runtime (claude --resume <id>, codex resume, …). Ids capturados em .tachyon/sessions.json (claude: sessão nomeada + uuid real do transcript; gemini: --session-id; codex/opencode: resolvido do transcript em disco). Agentes ad-hoc sobrevivem no ledger (com lineage), badge honesto · resumable vs · fresh start checado antes do clique, e um /resume feito dentro do TUI é seguido quando a atribuição é inequívoca.

src/resume/ · src/activity/

Fork de sessão

Pergunte algo fora da tarefa sem descarrilar o agente: o fork é um irmão novo carregando a conversa até o instante do fork (snapshot, não espelho). Se o original roda em worktree, o fork ganha worktree própria a partir do HEAD commitado. Capacidade nativa do runtime: só claude tem (--fork-session); runtimes sem fork simplesmente não mostram a ação — nenhuma imitação com perda.

Isolamento

Worktree — agentes paralelos, um branch cada

worktree: true inicia a sessão do agente em worktree git própria, branch própria — agentes paralelos nunca sobrescrevem os arquivos uns dos outros e o trabalho vira um branch revisável. Mecanismo git puro (qualquer runtime). Sub-agentes compartilham a worktree do pai (1 unidade de trabalho = 1 branch = 1 PR). worktreeSetup roda uma vez na criação. Limpeza é decisão humana: branch só é auto-deletada se Tachyon a criou e está merged. Verify gate: declare verify: e o agente ganha ação Verify + badge (✓/✗/⊘) atado ao commit — evidência de que o branch é entregável, nunca bloqueio de merge. Create PR empurra o branch e abre PR via gh com o veredito no corpo.

Harness isolado + isolamento de transcript

harness: dá a um agente seu próprio MCP/rules/skills/hooks sem vazar para a frota: Tachyon materializa um config-home privado (.tachyon/harness/<agente>/, CLAUDE_CONFIG_DIR), MCP com --strict-mcp-config (só os servidores declarados + o Bridge, sempre injetado). Segredos só como ${VAR} (literal é rejeitado); credenciais via symlink. isolate: transcript é a versão leve: home próprio (histórico atribuível, /resume sem ambiguidade) sem escopar nada. Três eixos independentes — transcript muda o config home, worktree muda o cwd, harness muda ambos com escopo; harness vence sobre isolate.

Orquestração declarativa

Pipelines — cadeia one-shot de agentes

Cadeia declarativa em .tachyon/pipelines/<nome>.yml (plan → implement → review). O run possui uma worktree que flui pela cadeia (worktree-as-state); o handoff opcional leva a narrativa (summary vira ## Upstream context do próximo nó). Dois modos: cadeia fixa (input: none) ou workflow reutilizável (input: required — rode uma vez por issue). Três formas de nó (especialista persistente / one-shot por exit code / LLM efêmero) e done-contract real: signal_then_verify exige complete_node (autenticado por nonce por nó) + gate verde + mudança real na worktree. gate: approve pausa o run para seu Approve/Reject; nó falho segura o downstream visivelmente bloqueado — sem retry silencioso.

Commands e runbooks — one-shots curados

Commands rodam uma vez e sair É o resultado: exit 0 = ✓, ≠0 = ✗ com dead pane preservado para inspeção. Namespace tmux próprio, sem toasts de crash. Para agentes, run_command é o jeito vetado de rodar procedimentos do projeto (retorna {passed, exitCode, durationMs, tail}; resultado pronto é reportado, não re-executado — rerun: true força). Runbooks encadeiam passos com gate de exit code: primeira falha para o procedimento, preserva o pane e marca o resto como skipped. run_host_action passa por um broker default-deny: capability com schema fechado, política pinada por sha256 (arquivo fora do workspace, modo 0600), trilha de auditoria hash-chained (à prova de adulteração) e transação durável — hoje a única capability é reloadWindow, recusada enquanto outro agente estiver ativo, com verificação do retorno após o reload (host/build errado é detectado, não presumido).

Schedules — cron por workspace, gated por humano

schedules: dá timers cron-like a qualquer runtime sobre os executores existentes (every/at × run comando/runbook ou spawn agente; catchUp para at perdido). Escopo honesto: dispara só com o workspace aberto — a extensão não é daemon. Pausar um schedule é memória de sessão — a config fica intocada.

Governança de delegação

Spawn gated — o contrato de delegação

Um spawn_agent com gate carrega um contrato estruturado: task / context / constraints + exatamente um de deliverable ou doneWhen, mais o gate (behavior_test + owns). Briefs longos vão losslessly para arquivo (.tachyon/briefs/spawn/) com só um ponteiro no pane (o tmux rejeita payloads grandes); teto rígido de 64KB por rejeição explícita, nunca truncamento silencioso. Para um behavior_test nomeado, o projeto configura explicitamente settings.verify.behavior (adapter, preparo isolado, comando, template do oracle e arquivos do executor). O arquivo deve existir, estar versionado e pertencer ao projeto antes do spawn; Tachyon fixa o hash dos seus bytes e exige o mesmo oracle em BASE e HEAD — nunca transforma prosa em asserção nem autoriza o implementador a editá-lo. O preparo cria o ambiente do runner em clones externos separados, e manifests/lockfiles/configs declarados também ficam presos aos hashes do spawn, sem confiar em dependências ignoradas do worktree. Como alternativa neutra de runner, cmd:<comando> verifica o comportamento sem presumir Vitest, npm ou test/unit; identificadores nomeados sem adapter são recusados de forma explícita pelo gate. Um primer advisory (TACHYON PRIMER no início, BEFORE FINISHING no fim, orçamentos de linha rígidos) deriva das mesmas configurações que o gate aplica — o exibido e o cobrado não podem divergir. Worktree de fixer é reutilizada por id de delegação, com recusa a alargar owns e a HEAD movida.

Tasks — board compartilhado com journal, evidência e protótipos

Fila de trabalho em arquivos (.tachyon/tasks/, um JSON por task t-<6hex>, escrita atômica) com máquina de status única (inbox → triaged → active → landed → done/dropped) — o board Mission Control deriva os drags permitidos da mesma tabela de transições, nunca re-codifica. Cada task tem journal append-only (com caps), doc rico opcional ancorado ao corpo por hash (edição externa do corpo sempre vence), anexos namespaced por task, e protótipos HTML autorados por agente validados fail-closed (cap 512KB, sem form/iframe/object) e renderizados só em sandbox estático sem script — aprovação registra o sha256 imutável como âncora única. next_task agenda por agente; flag_for_human marca awaitingHuman (autorado, nunca derivado; qualquer transição de status limpa). verify_task é o portão de verificação (~1000 linhas): resolve o sujeito pela Delivery, proíbe auto-waiver (caller vs todos os ocupantes), e produz achados codificados — no_commit, scope_breach (vs owns), teste de comportamento que deve FALHAR no baseSha e passar no head, tripwires de supressão de teste, histórico não-linear, worktree suja — com registro integrity-hashed publicado em transação.

Delivery + Git delivery — o registro durável da delegação

Duas camadas. A Delivery canônica (SQLite, .tachyon/deliveries-v2.sqlite3) é o ledger da ocupação de uma worktree gated do spawn ao verify: máquina de lease (free/pending/held/draining/verifying/quarantined/abandoned), segmentos de delegação (implementer → reviewer → fixer → verifier), identidade cercada por processo (pid + start + bootId) — ocupante improvável é recusa, nunca chute; reconciliação pós-reload é somente-leitura e bloqueia spawn/resume genérico nos agentes afetados. O GitDelivery é a projeção git: um registro por branch/worktree delegada com fases open → in_review → accepted → integrated/abandoned/pruned. integrate nunca roda comando git que mute o main — só registra integrated depois que o git prova containment do branch; prune recusa perder commits não contidos na base (a menos que explicitamente condenados); mutações em registros linked exigem caller privilegiado ou allowlist explícita — igualdade de nome nunca dá autoridade. Perfis de política: solo/balanced/strict (strict exige aceite não-próprio).

Probes — segunda opinião headless e capturada

Um probe é um processo filho simples (nunca um pane tmux) cuja resposta é lida dos arquivos de artefato do próprio runtime (claude -p --output-format json; codex exec --output-last-message), nunca do stdout cru. Arquétipos com schema de saída de máquina (adversarial-review, factual-verify, freeform) carregam guardas de framing (anti-viés, anti-fabricação) como propriedade do arquétipo, não do caller. Toda execução vira um envelope com razão de término normalizada (ok/model_error/refused/budget/timeout/parse_error/…); sem auto-retry (probe gasta budget); cap de concorrência e autorização antes de qualquer spawn; artefatos com cap de tamanho e retenção por idade + contagem em .tachyon/probes/. Intento de sandbox (read-only / workspace-write) mapeado para a flag nativa de cada runtime.

Humano no loop — aprovações, atenção e flags

Continuidade e handoff de projeto

Continuidade é a memória de trabalho por agente para sobreviver a compactação//clear/restart: um brief markdown autorado pelo agente em .tachyon/continuity/<agente>.md (frontmatter carimbado pelo Tachyon) + estado próprio do Tachyon que decide quando re-injetar o ponteiro no pane — um resume limpo nunca re-injeta em dobro, brief com status done nunca é injetado como trabalho ativo, escrita é atômica. Handoff é o estado curado do projeto, compartilhado e git-trackável: .tachyon/HANDOFF.md canônico (reescrita total protegida por compare-and-swap com token de revisão sha256) + notas estruturadas append-only em handoff-notes.jsonl (completed·blocked·decision·gotcha·next) — agentes nunca reescrevem o canônico diretamente, só anexam; um watermark forward-only mede o que falta destilar e a "velhice" é computada de atividade, não de mtime.

Roles e re-âncora pós-compactação

Um role é um contrato de tarefa reutilizável (coder / reviewer / tester / orchestrator / custom), nunca uma persona: o template abre o prompt e suas instructions: são anexadas depois (estende, nunca substitui); o contrato durável vai para .tachyon/roles/<agente>.md. Quando o CLI compacta a própria conversa (detecção best-effort por marcadores, claude + codex), a re-âncora digita um ponteiro de uma linha para o doc de papel — não re-digita o contrato inteiro. Filhos spawnados via Bridge recebem um guidance tail (coordene por pins/handoff/spawn_agent; rode seu verify gate antes de reportar done), desligável com settings.bridgeGuidance: false.

Plugins

Sistema de plugins

Um plugin é um diretório buscado do git (github:org/repo@ref, cache content-addressed verificado por SHA) com manifesto tachyon-plugin.json: um agregado dos blocos nativos de cada runtime (hooks por runtime, sem abstração cross-runtime) + skills/, MCP, git hooks e tools provisionadas (download https-only, pinado por checksum, instalação atômica imutável). Instalação em duas fases: preview nunca escreve; apply re-deriva o preview e recusa em drift do workspace (guarda TOCTOU por fingerprint de consentimento). O consent drawer mostra proveniência, cada comando shell que rodará em eventos de agente, escritas de arquivo e downloads com hashes. O lockfile committado (.tachyon/plugins.lock.json) é a única raiz de confiança: o launcher (.tachyon/bin/_tachyon-tool) re-valida o binário contra o pin por hash de fd (O_NOFOLLOW) antes de cada exec — até de um git hook sem VS Code rodando; uma launchPolicy declarada força env/args de segurança e recusa argumento que a sobrescreva (fail closed). Uninstall remove só o que o Tachyon escreveu (entrada editada pelo usuário vira órfã conservadora, nunca clobber). Webviews de plugin são não-confiáveis: recebem só uma projeção sanitizada da frota e uma única ação brokered com rate-limit.

Superfícies de UI

Sidebar — a frota em um webview

A TreeView nativa foi aposentada: a sidebar é um webview Preact renderizando exclusivamente a partir de view-models puros (AgentVM/FleetVM, testáveis sem vscode) — agentes (aninhados por lineage de spawn_agent; órfãos promovidos à raiz, filhos nunca são cascade-killed), pins, tasks, commands, schedules e pipelines, com contagens e ações inline ▶/■/↻/⑂/verify/PR gated por uma matriz de capacidades em código (não em when-clauses do package.json). Wedge watchdog

Um servidor tmux longevo pode travar (vivo mas sem responder — quirk upstream visto em tmux 3.6/WSL2). O watchdog sonda o socket num timer e, com wedge confirmado em dois checks consecutivos, auto-recupera: SIGKILL no servidor travado, limpa o socket, loga snapshot ps para caça upstream e avisa você — as conversas voltam via resume. Adaptadores de runtime

Uma tabela de 8 runtimes (claude, codex, gemini, grok, antigravity, opencode, qwen, continue) declara como cada CLI cunha ou captura id de sessão, se tem fork nativo, onde ficam os transcripts e o formato de harness isolado (CLAUDE_CONFIG_DIR / CODEX_HOME / tripla XDG). Segurança

Local-only: Bridge em 127.0.0.1, nunca na rede; sem nuvem/telemetria/conta. Bearer auth Bridge-resolved: cada agente ganha token próprio (TACHYON_AGENT_BRIDGE_TOKEN) cunhado a cada spawn/restart/resume — o Bridge resolve quem você é pelo token; declarar identidade alheia é caller_mismatch estruturado. O Bridge guarda só digests HMAC de comprimento fixo, nunca o plaintext. Tokens em storage privado (0600)/keychain, nunca em arquivo committável. Isolamento por workspace: sessões, porta, token e pins namespaced por hash do caminho. Guardrails: maxAgents, recusas de rename/delete em execução. Proveniência de build: na ativação, cada arquivo de dist/ é re-hashado contra o provenance.json embutido — build sujo ou divergente gera aviso de "build não verificado". Diagnósticos passam por redação de tokens (match exato + padrões sintáticos). Modelo de ameaça honesto: loopback bloqueia a rede; malware same-user está fora de escopo (fronteira da plataforma).
